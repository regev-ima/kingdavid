# הרשאות ותפקידים

מערכת ההרשאות של King David — ארבע רמות הרשאה, קטלוג של 185 יכולות, וחריגים
פר-נציג.

> **הכלל שמעליו אין:** המערכת הזו לא מורידה לאף אחד שום דבר. ביום שהיא עלתה, כל
> משתמש קיבל בדיוק את מה שהיה לו יום קודם. כל מה שהיא מוסיפה זה את היכולת *לראות*
> את ההרשאות ו*לשנות* אותן.

---

## רמות ההרשאה

```
נציג  <  מנהל חנות  <  מנהל ראשי  <  סופר אדמין
```

| רמה | `access_level` | מה היא |
|---|---|---|
| נציג | `rep` | עובד שטח — הלידים, ההצעות וההזמנות שלו |
| מנהל חנות | `store_manager` | הצוות והפעילות היומיומית: כל הלידים, שיבוץ משמרות, ניהול שירות |
| מנהל ראשי | `chief_manager` | ניהול חוצה-ארגון: כספים, שיווק, נציגים ורוב ההגדרות |
| סופר אדמין | `super_admin` | הכול, כולל עריכת מערכת ההרשאות עצמה. נתנאל ורגב |

הרמה יושבת בעמודה חדשה, `users.access_level`, ולא ב-`users.role`. `role` נשאר
בדיוק כפי שהיה: הוא זה שמייצר את התפריט הצדדי, את כל שערי ה-`canAccess*`
ב-`lib/rbac.js`, ושלוש מדיניויות RLS. הוספת שני ערכים אליו הייתה מפנה את כל
אלה בבת אחת. `access_level` הוא ציר שני, מוסיף בלבד.

**מה סופר אדמין יכול ואף אחד אחר לא:** לערוך את מטריצת ההרשאות, למנות סופר
אדמין נוסף, ולהגדיר חריגים אישיים. שום יכולת תפעולית לא נלקחה מאף מנהל קיים —
היכולת היחידה ששמורה לסופר אדמין היא חדשה, ואף אחד לא החזיק בה קודם.

**חלון האתחול:** כל עוד אין אף סופר אדמין במערכת, כל `role = 'admin'` יכול
לפתוח את מסך ההרשאות (`canManagePermissions`), והמסך אומר את זה במפורש. אחרת
סביבה חדשה נועלת את עצמה מחוץ לפיצ'ר.

## איפה זה במסך

| מה | איפה |
|---|---|
| מטריצת ההרשאות לפי רמה | הגדרות ← הרשאות ותפקידים ← רמות הרשאה |
| מינוי סופר אדמין | הגדרות ← הרשאות ותפקידים ← סופר אדמין |
| רמת הרשאה + חריגים לנציג | הגדרות ← נציגים ← נהל נציג ← הרשאות |

## סדר ההכרעה

`can(user, key)` עונה על שאלה אחת, לפי הסדר הזה:

| # | מקור | מה קורה |
|---|---|---|
| 0 | סופר אדמין | מותר. סוף. |
| 1 | סעיף אב חסום | אסור — וכל תת-הסעיפים איתו |
| 2 | חריג אישי (`users.permission_overrides`) | מכריע, לכאן או לכאן |
| 3 | הרשאה אישית קיימת (`users.extra_permissions`) | מותר |
| 4 | מטריצת הרמה (`role_permissions`) | מכריעה, לכאן או לכאן |
| 5 | ברירת מחדל | השער הישן, באיחוד עם ברירת המחדל של הרמה |

שלוש נקודות שכדאי להבין בשלב הזה:

**שלב 5 הוא הסיבה ששום דבר לא השתנה.** לכל הרשאה בקטלוג שמתאימה לשער שכבר קיים
באפליקציה יש `baseline` — מזהה של אותו שער. כשאין הגדרה מפורשת, התשובה היא
התשובה הישנה. מטריצה ריקה + אפס חריגים = בדיוק המצב שהיה.

**שלב 3 לפני שלב 4 הוא בכוונה.** נציג שיש לו `extra_permissions.view_finance`
לא מאבד את הכספים כשמנהל מכבה `finance.view` לרמת "נציג". ההרשאה האישית היא
ההחלטה הספציפית יותר; רק חריג אישי מפורש (שלב 2) יכול לבטל אותה.

**שלב 1 הוא כל הסיפור של ההגדרות.** אפשר לחסום את כל מסך ההגדרות
(`settings.access`), או סעיף בודד בתוכו (`settings.statuses`), או תת-סעיף בתוך
הסעיף (`settings.statuses.colors`) — הכול נובע מהכלל האחד הזה, בלי טיפול פרטני
לאף צומת.

### גבול הסביבה

`inferAccessLevel()` ממפה כל לא-אדמין ל"נציג", כך שעובד מפעל ונציג מכירות נוחתים
על אותה רמה — בעוד שברירות המחדל של רמת "נציג" בקטלוג נכתבו עבור נציג מכירות.
לכן ברירת מחדל של רמה **לא יכולה** להעביר משתמש מעבר לגבול הסביבה שהתפקיד שלו
מצייר (`isWorkspaceBaseline` ב-`baselines.js`). מעבר בין סביבות הוא עדיין שינוי
של `role` / `department`, בדיוק כמו היום. הענקה מפורשת עדיין פותחת יכולת בודדת.

## הקוד

```
src/lib/userScope.js              הפרימיטיבים (isAdmin, getUserScope, …)
src/lib/permissions/

  catalog.js                      185 ההרשאות, מקובצות ומקוננות
  baselines.js                    מה כל הרשאה שווה היום
  resolve.js                      מנוע ההכרעה — can(), explain()

src/hooks/usePermissions.jsx      ההוק שמסכים משתמשים בו

src/components/settings/PermissionsTab.jsx

```

`lib/userScope.js` קיים כדי לשבור מעגל: `lib/permissions` צריך את בדיקות התפקיד
הישנות כדי לחשב `baseline`, ו-`lib/rbac.js` צריך את המנוע. הפרימיטיבים יושבים
לבד, והכול מייבא מהם כלפי מטה. `rbac.js` מייצא אותם מחדש, כך שכל
`import { isAdmin } from '@/lib/rbac'` קיים ממשיך לעבוד.

### שימוש במסך

```jsx
const { can } = usePermissions();
{can('finance.view') && <FinanceCard />}
```

### שני שערים, שתי משמעויות

`can()` שואל "מותר?". `isExplicitlyBlocked()` שואל "מישהו כיבה את זה במפורש?".

התפריט הצדדי משתמש ב-`isExplicitlyBlocked`, לא ב-`can`. התפריט הוא טבלה
מתוחזקת ביד לכל תפקיד, והיא מעולם לא נדרשה להסכים עם ה-baselines של הקטלוג;
`can()` שם היה מסתיר פריטים שעובדים מצוין היום ברגע שה-baseline חולק עליהם.
`isExplicitlyBlocked` הוא no-op עד שמישהו באמת מוריד מתג.

השערים המורכבים ב-`lib/rbac.js` עוברים דרך `gate()` שמשלב את שניהם: מרחיב עם
`can()`, מצמצם רק על חסימה מפורשת, והכלל הישן נשאר הרצפה.

## אבטחה

| מה | איפה נאכף |
|---|---|
| `access_level`, `permission_overrides` — לא ניתנים לעריכה עצמית | טריגר `prevent_users_privilege_escalation` |
| רק סופר אדמין ממנה סופר אדמין | אותו טריגר (חל גם על אדמינים) |
| רק סופר אדמין כותב ל-`role_permissions` | RLS + `can_manage_permissions()` |
| אי אפשר להעניק הרשאה שאין לך | `canDelegatePermission` |
| אי אפשר להעניק רמה ששווה לשלך או גבוהה ממנה | `canGrantAccessLevel` |

שתי השורות האחרונות הן הגנות UI. השלוש הראשונות מוחזקות במסד — מי שיכול לערוך
הרשאות יכול להעניק לעצמו כל דבר אחר, ולכן השער הזה חייב להחזיק גם מול קריאת API
ישירה.

## הוספת הרשאה חדשה

1. הוסיפו צומת ל-`PERMISSION_GROUPS` ב-`catalog.js` — `key`, `label`,
   `description`, `baseline`, `tiers`.
2. אם קיים כבר שער לזה באפליקציה, תנו לו את ה-`baseline` המתאים. אם לא —
   `BASELINE.NONE`, וברירות המחדל של הרמות יחליטו.
3. קראו ל-`can(user, 'the.key')` במקום שבו זה נאכף.
4. `npm run check:permissions`.

הרשאה בקטלוג בלי קריאה ל-`can()` היא לא באג — היא אוצר המילים שהמסך חושף, וחיבור
שלה מאוחר יותר הוא שינוי של שורה אחת שלא יכול לשנות התנהגות בשקט, כי ה-`baseline`
שלה כבר מתאר את המצב הקיים.
